# ADR 0002: Pin pnpm globally in the backend Dockerfile

- Status: accepted
- Date: 2026-08-09

## Context

The Docker image build failed at `pnpm exec medusa build` (exit 1) with a
pnpm-internal stack trace (`runDepsStatusCheck -> sync2`). Root cause: the
repo pins `pnpm@10.11.1` (root `packageManager`) and the lockfile
(`lockfileVersion: '9.0'`) was generated by pnpm 10.x. But
`apps/backend/package.json` and `apps/storefront/package.json` carry **no**
`packageManager` field, so when the `builder` stage runs from
`/app/apps/backend`, corepack finds no `packageManager` and falls back to the
Node 22 distro default pnpm (11.21.0). pnpm 11 then runs a deps-status check
against a `node_modules` installed by 10.11.1 and aborts.

## Decision

Pin pnpm globally in the `base` stage with
`RUN corepack enable && corepack prepare pnpm@10.11.1 --activate`, so every
build stage uses 10.11.1 regardless of the working directory's
`packageManager` field.

Alternative considered — adding `packageManager` to each sub-package's
`package.json`: rejected. It scatters the version across files and is easy to
forget on any newly added package; the global `corepack prepare` enforces the
single source of truth from the root `packageManager`.

## Consequences

- The build no longer depends on which directory corepack resolves from.
- pnpm version is defined in one place (root `packageManager`) and enforced in
  the image via `corepack prepare`.
- If the root `packageManager` is bumped, update the `corepack prepare`
  argument to match.
